## 1. Executive Summary: What Does the AI Actually Do?

A critical scientific distinction must be established before answering any question regarding "accuracy":
> **The AI in this framework does NOT scan ports, guess passwords, or blindly execute exploit payloads.**  
> Instead, the AI operates as an **Exploit Usability Pre-Assessor (GAP-1)**. It analyzes candidate Proof-of-Concept (PoC) code and vulnerability intelligence prior to execution to predict exploit viability and assign structured quality scores.

Traditional vulnerability scanners (e.g., Nessus, OpenVAS, Nuclei, ZAP) suffer from high false-positive rates because they identify vulnerabilities based solely on passive banners or surface regexes. Naive autonomous agents (e.g., AutoGPT, raw PentestGPT) frequently deadlock because they select high-CVSS exploits whose public PoC code is unmaintained, corrupted, platform-incompatible, or syntax-broken.

GAP-1 introduces an AI-driven pre-execution filter that examines exploit code structure, required privileges, dependencies, and delivery mechanism before assigning a quantitative priority score.

## 2. Mathematical Scoring Formulation (GAP-1)

For every candidate vulnerability $c_i$, the framework computes a final composite priority score $S(c_i)$ used to order the candidate action queue:

$$S(c_i) = P_{\text{exploit}}(c_i) \times W_{\text{quality}}(Q(c_i))$$

Where:
- $P_{\text{exploit}}(c_i) \in [0.0, 1.0]$ is the raw exploit probability derived from the Exploit Prediction Scoring System (EPSS) or normalized scanner detection heuristics.
- $Q(c_i) \in \{\text{HIGH}, \text{MEDIUM}, \text{LOW}\}$ is the categorical exploit usability rank generated by the LLM via structured output.
- $W_{\text{quality}}$ is the discrete quality weighting factor:
  $$W_{\text{quality}}(Q) = \begin{cases} 
  1.00 & \text{if } Q = \text{HIGH} \\ 
  0.70 & \text{if } Q = \text{MEDIUM} \\ 
  0.40 & \text{if } Q = \text{LOW} 
  \end{cases}$$

### 2.1 The Operational Effect of Pre-Assessment
Consider two candidates discovered during surface mapping:
- Candidate $A$: CVSS 9.8, EPSS 0.85, but its public PoC is broken or missing dependencies ($Q = \text{LOW}$).  
  $$S(A) = 0.85 \times 0.40 = \mathbf{0.34}$$
- Candidate $B$: CVSS 7.5, EPSS 0.55, with clean, verified, standalone Python exploit code ($Q = \text{HIGH}$).  
  $$S(B) = 0.55 \times 1.00 = \mathbf{0.55}$$

Without GAP-1, a standard scanner or naive agent executes Candidate $A$ first, fails repeatedly, exhausts time and network budget, or triggers intrusion detection systems. With GAP-1, the engine dynamically reorders Candidate $B$ ahead of Candidate $A$ ($0.55 > 0.34$), resulting in immediate successful verification on the first attempt.

## 3. Structural Output Schema & Guardrails

To prevent LLM hallucination and ensure strict JSON compatibility, all LLM calls are bound to Pydantic structured schemas via LangChain:

```python
class UsabilityRank(str, Enum):
    HIGH = "HIGH"      # Production-grade, zero-dependency, verified reliable
    MEDIUM = "MEDIUM"  # Functional but requires specific parameters or environment
    LOW = "LOW"        # Pseudo-code, broken syntax, missing payloads, or dangerous

class ExploitAssessment(BaseModel):
    cve_id: str
    usability_rank: UsabilityRank
    confidence: float = Field(ge=0.0, le=1.0)
    requires_auth: bool
    delivery_mechanism: str
    reliability_rationale: str
```

### 3.1 Hallucination Defense & Deterministic Fallback
If the LLM generates invalid JSON, exceeds inference timeout ($12.0\text{s}$), or returns an unparseable rank, the framework engages the **fail-safe fallback**:
1. Scans are never blocked by an unresponsive LLM.
2. The finding reverts to deterministic baseline scoring derived from offline CVE corpus labels.
3. The assessment provenance is explicitly tagged in the run metadata:
   ```json
   "assessor_mode": "fallback",
   "fallback_reason": "LLM inference timeout or unparseable schema"
   ```

## 5. Verification vs Assessment: Ground Truth Separation

A common mentor question is: *"Is your LLM 100% accurate?"*  
The scientifically rigorous answer is:
> **The LLM is an estimator, not an oracle.**  
> Pre-assessment accuracy measures how well the LLM's usability rank correlates with real exploit success. However, **no vulnerability is confirmed or marked true positive by LLM prediction alone.** Confirmation requires active, non-destructive HTTP verification.

### Empirical Proof from `scripts/run_reliability_evaluation.py`:
- **Scanner Detection Layer Alone:** Precision = **40.0%**, Recall = 100.0%, False Positives = 6 out of 10 cases.
- **Active Verification Layer:** Precision = **100.0%**, Recall = 100.0%, False Positives = **0**.
- **Inconclusive Handling:** 2 out of 10 cases (HTTP 500 error and connection timeout) were isolated into the `INCONCLUSIVE` tier with zero false claims.
