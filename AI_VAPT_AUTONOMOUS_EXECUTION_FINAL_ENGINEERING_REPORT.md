## 0. Executive verdict

**The autonomous assessment does not yet work end-to-end.**

What is genuinely proven:

- The most serious defect — a run being reported as a successful autonomous assessment when only bookkeeping or generic HTTP-probe activity occurred — is closed in code, covered by new regression tests, and verified against both real and simulated run data.
- The configured cloud-hosted model demonstrably participates: real LLM requests, real model-generated `curl` commands, and real subagent dispatch were observed against the live Juice Shop instance.
- **A complete model-driven run (`real-e2e-kaggle`) terminated cleanly**: the model itself called `finish_scan`, the final report and SARIF were written, and the evidence gate classifies the run as genuine (53 LLM calls, 48 security-tool calls).
- GAP-1 ranking is genuinely injected and active in the web-worker execution path.
- Engine and API use separate run directories; stale-state quarantine, no-progress stall detection, and honest failure classification work on real runs.
- The full regression suite is green: **2935 passed, 1 skipped, 3 xfailed, 0 failures**.

What is not proven:

- The completed run produced **0 confirmed vulnerabilities** and a final report whose executive summary and technical analysis describe generic Juice Shop categories rather than evidence from this run — the report is honest about "no exploitable vulnerabilities detected", but it is not a substantive evidence-backed assessment.
- No **GAP-enabled** run reached a clean `completed` state: `run-043060b0` failed at its 600s wall-clock limit.
- GAP-2 pivoting is covered by isolated tests but was **not** conclusively demonstrated live: the engine run.json briefly reported `gap2_pivots=2`, but the authoritative control-plane record finished with `gap2_pivots=0` and only a `GAP1_ROOT_TASK_INJECTED` event.
- The supplied Kaggle endpoint is too slow/flaky for the configured wall-clock budgets (a GAP web run failed at 600s; the completed CLI run still logged 6 HTTP 524 stream timeouts and 12 errored LLM requests among 53 successes).

No claim of completion is made on the basis of generic HTTP probes, bookkeeping-only candidate transitions, mocked model responses, or isolated unit tests.

## 1. Actual root causes

### 1.1 False success in the engine (`strix/core/runner.py`)

After the "guaranteed real candidate investigation" block (automated HTTP probes against GAP-1 candidates), the runner performed this sequence:

1. Computed `unresolved` from `gap_run.candidates`.
2. If no candidates remained unresolved, wrote `report_state.scan_results` with `"scan_completed": True` and `"success": True`, including a polished executive summary, methodology, and technical analysis.
3. Called `report_state.save_run_data(mark_complete=True)`.
4. Set the root agent status to `completed` under the coordinator lock.
5. Executed `return None` — **skipping `run_agent_loop` entirely**.

An in-code comment explicitly stated: "The run is complete; return without entering the model-driven agent loop (which the weak provider cannot drive productively)." This is the direct implementation of the reported failure mode: a truthful-looking, completed report generated by probes and candidate bookkeeping with zero model reasoning. I verified this code existed before my edits; it was not a prior agent's misreport.

### 1.2 No execution gate in the API worker (`strix/interface/api.py`)

`_execute_run_worker` treated a clean subprocess exit (`ret_code` 0 or 2) plus an underlying `run.json` with `"status": "completed"` as sufficient to set the control-plane run to `completed` or `partial`. Trusted signals included:

- candidate counters (`candidates_investigated`, `pivots_count`),
- decision-trace events (`GAP2_SUCCESS`),
- status labels in the engine `run.json`.

None of these prove that the model reasoned or that a security tool touched the target. A bookkeeping-only subprocess could therefore complete successfully from the dashboard's point of view.

### 1.3 Contributing findings confirmed but already fixed before this session

These were real defects identified by earlier agents; I verified the current implementation rather than trusting the reports:

- `gap_bridge.record_outcome` rejects a "positive" outcome lacking a real vulnerability `report_id`, downgrading it to `observed`. This prevents GAP-2 success events built from narrative coverage.
- `_engine_run_name()` gives the CLI worker a distinct `<run-id>-engine` directory, so worker and engine no longer race on the same `run.json`.
- `_quarantine_stale_running_run()` converts persisted `running` records with no live process into `interrupted` with reason/end time.
- `should_stop_for_no_progress()` and `_is_productive_tool()` exist and distinguish real tool work from `record_coverage`/`finish_scan` bookkeeping.
- The frontend stop-polling list already includes `interrupted`, `partial`, `blocked`, `provider_blocked`.

### 1.4 Measuring defects that are NOT application bugs

- The supplied Kaggle endpoint returned `HTTP 524 stream_first_event_timeout` 6 times during the CLI run, with automatic retries. Some successful calls took 89–121 seconds. This is a provider/tunnel reliability limitation, not a false-completion defect.
- The persisted CLI config points at `STRIX_LLM=openai/custom-org/llama-3.3-70b` with `LLM_API_BASE=https://api.openai.com/v1` and an inconsistent `LLM_EXTRA_BODY` (`num_ctx: 32768`) versus `STRIX_CONTEXT_FALLBACK_TOKENS=131072`. I did not change it; per constraints I passed the supplied endpoint only via environment variables and in-memory runtime credentials.

## 3. Functional changes made

### 3.1 `strix/interface/api.py`

Added:

```python
def execution_evidence_from_logs(logs) -> dict[str, int]
def execution_evidence_from_run(run_data, log_text="") -> dict[str, Any]
def has_genuine_assessment_execution(run_data, log_text="") -> bool
```

Behavior:

- Counts `Calling LLM` lines in engine stdout/log as model participation.
- Counts `Invoking tool <name>` lines only when `_is_productive_tool(name)` is true (coverage/finish/report tools excluded).
- Cross-checks optional telemetry arrays `llm_requests` and `tool_calls`, which exist only when `STRIX_RUN_RECORD_TIMINGS=true`; takes the maximum of log-derived and telemetry-derived counts.
- Never treats a status label, candidate counter, or decision-trace event as evidence.

Worker integration:

- After subprocess exit, computes `run_entry["execution_evidence"]`.
- In the **final success branch only** (so genuine failure/pause classifications are not altered), if either model participation or security-tool execution is missing:
  - sets `exit_code_interpretation = "no_genuine_execution"`,
  - sets status `failed`, `failure_classification = "failed_agent"`, `report_status = "no_findings"`,
  - writes an explicit error naming the recorded call/tool counts,
  - sets progress below 100% with phase `Failed: no genuine autonomous execution`,
  - appends a `RUN_FAILED` event and finalizes the lifecycle.

Telemetry reliability:

- `_sync_telemetry(final_sync=True)` re-reads the entire engine log after process exit with a short settle, so late turn writes are captured regardless of polling timing.

### 3.2 `strix/core/runner.py`

Deleted the entire probe-then-complete block (approximately 60 lines). Replaced with an explanatory log line:

```
Automated GAP-1 probes finished for N candidate(s); handing control to the autonomous model loop
```

`run_agent_loop` is now unconditional after probing. Truthful completion is written only by the agent/finish path or by legitimate terminal handlers (MaxTurnsExceeded, budget exceeded, rate limit).

### 3.3 Tests

New: `tests/test_autonomous_execution_truthful_completion.py` (5 tests):

1. `test_execution_evidence_from_logs_counts_only_real_work` — 2 LLM calls, 2 security tools from a mixed log.
2. `test_execution_evidence_rejects_bookkeeping_only_run` — 8 abandoned candidates + GAP2_SUCCESS trace + coverage/finish calls → genuine=False.
3. `test_execution_evidence_accepts_model_and_security_tools` — genuine=True.
4. `test_worker_completion_gate_requires_execution_evidence` — AST check that the gate precedes the completed assignment inside `_execute_run_worker`.
5. `test_runner_does_not_shortcut_complete_before_model_loop` — AST check that the old "Assessment complete after GAP-1 investigation" block is gone.

Updated success-asserting legacy fixtures to emit realistic evidence:

- `tests/test_phase2_execution_reliability.py`

1. **No clean end-to-end completion.** Neither real run reached a final `completed` state with reconciled artifacts. The CLI run was still active; the GAP web run failed at 600s.
2. **Provider reliability.** The supplied Kaggle endpoint produced 6 HTTP 524 stream timeouts and ~90–121s successful calls. It is not currently reliable enough for a bounded full assessment.
3. **GAP-2 live demonstration missing.** Tests cover pivoting; live counters disagree between engine and control plane. No pivot was confirmed as genuinely dispatched and executed.

The user must restore it if the frontend should persistently use the supplied endpoint. I did not modify it, invent credentials, or switch providers.
5. **Zero findings.** The verification-state/report-classification pipeline could not be exercised against real confirmed vulnerabilities.
6. **Validation-scope artifacts.** `tests/helpers_real_execution.py` is an unused helper; harmless but could be removed in a later cleanup.
7. **Repository hygiene.** No commits, pushes, branch switches, or release publication were performed, per constraints.

## 9. Final verdict

**The autonomous assessment does not work end-to-end.**

The false-success architecture has been removed and replaced with an execution-evidence gate; the configured cloud model demonstrably reasons and drives real `curl`/sandbox security tools; GAP-1 injection is live in the worker path; the full test suite is green; and engine/API run separation plus honest failure classification are verified on real runs.

However, no model-driven run has completed cleanly with consistent engine/API/dashboard terminal state, no live GAP-2 pivot is confirmed, no confirmed vulnerability was produced, and the hosted endpoint is unreliable within configured budgets. This report therefore does not claim end-to-end success. The next concrete step is to restore a reliable endpoint (or raise wall-clock/stream timeouts with operator approval), let a GAP-enabled run finish, and reconcile its engine/API artifacts before changing the verdict.
